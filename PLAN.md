# Plan: BL-92 — counting_direction toggle (companion + Android app)

## Summary
Expose the two new BL-92 global runtime settings — `counting_direction_mode` (`"auto"` | `"manual"`, default `"auto"`) and `counting_direction` (`"up"` | `"down"` | `"left"` | `"right"` | `null`, manual only, default `null`) — in the Jetson companion HTTP bridge (`PUT/GET /api/settings` routing + validation) and the Android Settings screen (Auto/Manual toggle + direction selector gated by the active `counting_line_orientation`), mirroring the existing BL-84/BL-88 toggle patterns.

## In Scope
- Companion: add the two keys to `_GLOBAL_SETTINGS_KEYS`, validate them in `_validate_settings_payload`, add a soft orientation-mismatch check when both are present in the same PUT, update the module docstring's recognised-keys list.
- Android: extend `JetsonSettings` (serialize/parse), `SettingsRepository` (DataStore cache + defaults), `SettingsViewModel` (flows + setters folded into the coalesced `scheduleSettingsPush`), `SettingsScreen` (new "Sens de comptage" section gated by orientation + reset-counter warning), strings (en + fr).
- Tests: add `counting_direction_mode` / `counting_direction` validation cases (valid/invalid/bool/null + orientation-mismatch soft-reject) to `tests/test_companion_settings_validation.py`.
- Docs: update `docs/01_jetson_companion.md` (recognised-keys list + curl example) and `docs/02_android_app.md` (Settings section description).

## Out of Scope
- No countingapp changes (BL-92 already merged in the sister repo).
- No `docs/IPC_CONTRACT.md` changes (already synced/byte-identical in both repos).
- No Jetson/counting pipeline validation in this repo.

## Architecture Decisions
- **Global top-level keys (not per-model).** Per the IPC_CONTRACT §runtime-settings example (lines 142-144) and the contract table note "Additive — companion byte-identical sync later", `counting_direction_mode` + `counting_direction` live at the top level of `runtime-settings.json` alongside the display/tracker toggles, NOT under `models.<active>`. Adding them to `_GLOBAL_SETTINGS_KEYS` makes `_resolve_settings_flat` return them on GET and `_merge_settings_per_model` write them to the top level on PUT automatically — the same mechanism already used for `draw_tracking`/`draw_mask_zones` etc.
- **Companion soft validation is self-contained to the same PUT.** The optional orientation-mismatch check only runs when both `counting_direction` and `counting_line_orientation` are present in the SAME PUT payload (cheap, no extra file read). Otherwise the value passes through unchanged and the authoritative reject+WARN stays in the countingapp's `main.py` (per the contract). This avoids the companion having to re-read `runtime-settings.json` to resolve the active orientation, which would couple it to the per-model active-model resolution.
- **Android direction selector reuses the existing `countingLineOrientation` flow.** The ViewModel already holds the live orientation (seeded from `GET /api/settings` + refreshed); no extra fetch is needed. Up/Down chips are shown when orientation is `"horizontal"`, Left/Right chips when `"vertical"` (matching the contract: horizontal line → up/down crossing; vertical line → left/right crossing).
- **Coalesced PATCH.** `setCountingDirectionMode`/`setCountingDirection` fold the two new keys into the existing debounced `scheduleSettingsPush` PATCH body (same coalescing as the tracking/offset keys), so rapid toggle flicker is one PUT.
- **Reset-counter warning in the UI.** A direction change resets the counter (per contract, like `counting_class_ids`). The Settings screen surfaces a warning string (mirrors `offset_warning`/`species_hot_reload_note`); the companion/countingapp handle the actual reset.
- **`counting_direction` cached as a nullable string.** Default `null` (manual not yet set / auto mode). The DataStore stores it as a string with a sentinel for null (empty string → null on read), mirroring the nullable-string pattern used for `countingLineOrientation` but allowing the explicit `null` PATCH semantics.

## Risks
- **Soft validation gap when orientation is NOT in the same PUT.** If the app sends only `counting_direction` without `counting_line_orientation` in the same PATCH, the companion passes it through and the countingapp does the authoritative reject+WARN. This is by design (the countingapp is the source of truth) but means a mismatch is only caught at recording start, not at PUT time. Mitigated by the Android UI gating the direction selector on the live orientation so a mismatched combo cannot be submitted from the app.
- **Nullable-string DataStore sentinel for `counting_direction`.** Storing null as an empty string requires the read path to map `""` → `null`; a future edit that forgets the coercion would treat an unset direction as `""` and serialize it as a non-null string on PUT. Mitigated by keeping the coercion inside the Repository getter (single point) and mirroring the existing nullable-string handling.
- **Coalesced PATCH ordering.** Folding the two new keys into `scheduleSettingsPush` means a mode flip + direction change in quick succession fire as one PUT — desirable, but the body always carries all current values, so a stale cached orientation could pair with a new direction. The Android UI gating (direction chips only enabled for the matching orientation) prevents the user from constructing an invalid combo from the app.
